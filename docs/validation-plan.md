# Validation plan

Host tests cover the Stage 2 policy, identity and persistence stores, the Stage 3 event engine and the Stage 4 supervisor state machine. **All module runtime and physical acceptance cases are Not run.** The [discovery checkpoint](discovery/reference-2026-11-04.md) contains unfiltered Stage 1 baseline observations and retained diagnostic failures. The unchanged specification §§4, 7, 16–17, 20 controls acceptance.

## Evidence rules

Each result records case ID, UTC execution time, operator, source commit and reviewed state, artifact SHA-256, complete environment, profile/mapping-evidence version, backend, requested/saved/active generation, expected outcome, observed outcome, Pass/Fail/Not run/Not applicable, count and evidence location. Not applicable needs a concrete capability-based reason; missing hardware is Not run. Keep raw private evidence outside Git; publish only reviewed sanitized extracts. Distinguish upstream documentation, engineering choice, synthetic fixtures, host execution, emulator loading, and physical measurements.

For physical environments record variant, Android/API, full ROM, kernel release/build, root implementation/fork and kernel/userspace/manager versions, executable ABI, page size, enforcing SELinux/service domain, accessory identity/transport/collections and Android mappings. Verify physical results against the release bytes or an identical recorded digest. Changing code, build flags or packaged bytes after acceptance requires the affected tests again.

An allowed event must cause its intended action exactly once without added action. A blocked event must not cause its targeted action in supported contexts. Audio, microphone, routing and unrelated controls need separate observations; silence does not prove preservation. Any wrong target, input loss, broken audio/microphone, unsafe policy or unreliable recovery blocks stable publication.

They cover the host portions of T02 and T05 and policy/storage inputs from T21. Android inventory and storage integration, an injected directory-sync fault after rename, and T23 migration and rollback remain later gates. [Host commands](build.md#stage-2-host-checks)

Stage 3 replays the six [synthetic protocol fixtures](../tests/fixtures/README.md) and 1,530 captured records across 510 sanitized Stage 1 frames into a host sink. Eleven session tests cover the host portions of T06, T15 and T19. The full 23-test workspace passed on arm64 macOS with Rust 1.99.1 and under AddressSanitizer with the pinned nightly. The policy and event harnesses each completed 100,000 coverage-guided inputs under AddressSanitizer. [Reproduction commands](build.md#stage-3-host-fuzzing-and-sanitizer) The [Stage 1 gap review](discovery/stage-1-gap-review-2026-11-05.md) separates missing discovery evidence from later prototype qualification.

Stage 4 host recovery work adds generation-checked pause, resume, next-boot disable/enable and restart-latch operations. Eight new store cases cover stale and exhausted generations, concurrent recovery requests, marker creation/removal, tampered markers, fail-safe partial writes, ordinary-edit rejection and enrollment revalidation. At that point the workspace had 31 passing tests. These are host portions of T24 and the boot-escape input to T28; physical pause, marker durability across reboot, root control exposure and the recovery drill remain Not run.

Stage 4 host supervision work adds a pure state machine with configurable start, progress, pause, kill and restart deadlines. Nineteen synthetic cases cover zero-deadline rejection, startup timeout, stalled and backward progress, equal and advancing counter samples, orderly pause within and beyond its deadline, unexpected exit, spawn failure, kill failure, unconfirmed termination, restart spacing, three-failure latching, explicit latch recovery, persisted and external latches, pause/boot-escape gating and restart cancellation. The workspace now has 50 passing tests. These are host portions of T16, T24 and the latch/boot-escape inputs to T28. No process adapter, progress transport, descriptor release, measured deadline, Android service behavior or physical drill is established.

The Linux process adapter adds ten tests that drive real `/bin/sh` workers. They cover orderly pause with confirmed group exit, escalation to kill for a worker ignoring `SIGTERM`, a stalled worker, an escaped descendant that must die before exit is confirmed, a malformed progress frame, an unreadable gate, a gate that closes before spawn, three failures persisting the latch once, worker death when the supervising thread exits, and the exclusive lock. On 10 November 2026 the workspace passed 70 tests in the pinned Rust 1.99.1 Alpine arm64 container on LinuxKit kernel `7.0.14-linuxkit`, with 20 further adapter-suite reruns of the final code passing, and 54 tests on macOS. This is host evidence only: no deadline is measured, and Android `/proc`, SELinux, signal and parent-death behavior are unverified.

The store-backed gate and the `earkey-drill` no-grab drill ran in the same container on 10 November 2026, against a tmpfs `/data/adb/earkey_control` (mode `0700`); the workspace passed 74 tests. All four drill scenarios passed in six consecutive runs: pause 11–12 ms, kill escalation 1,013–1,021 ms (the 1 s pause deadline plus `SIGKILL`), stall detection 501–510 ms (the 500 ms progress deadline) and parent-death cleanup 10–13 ms. No worker process survived. The drill refused missing storage, the `stay-inactive` marker (`boot_disabled`) and a `0755` storage directory, and rejected extra arguments. These are container timings with synthetic limits, not phone measurements or production deadlines. On the reference phone, the v11 services-hook run passed the same four scenarios: pause 105 ms, kill 1,074 ms, stall 560 ms and parent death 10 ms ([result](prototype-preflight.md#service-context-supervision-drill-result--10-november-2026)).

The worker inventory has 7 tests. Three run on any host: bitmap decoding, rejecting a regular file as an input node, and the node limit. Four run on Linux with real character nodes. They show that a reference-shaped sysfs node yields exactly one `Policy::targets` match with the reference fixture, that virtual and gpio nodes carry no USB identity and select nothing, that mismatched, symlinked or unreadable nodes fail the scan, and that a changed HID directory shape drops the USB identity. On 10 November 2026 the workspace passed 81 tests in the pinned arm64 container with only `CAP_MKNOD`. Host fixtures do not establish the phone's sysfs layout on the new kernel.

The environment reader has 3 host tests. The reference phone's measured values match only the reforge evidence, a Stage 1-shaped `/proc/version` matches only the Stage 1 evidence, and every missing, empty, control-character, 91-byte or non-numeric property and every malformed `/proc/version` is rejected. The device module has 3 Linux tests: its ioctl encodings equal the kernel values (for example `EVIOCGID` is `0x80084502`), byte bitmaps decode to the reference key set, and a non-evdev character node, a different inode and a regular file are rejected. On 10 November 2026 the workspace passed 92 tests in the pinned arm64 container. On the reference phone, the v12 services-hook run passed `earkey-worker check` against the real earphone node, including the `EVIOCG*` revalidation and the neutral check ([result](prototype-preflight.md#service-context-worker-check-result--10-november-2026)).

The proxy has 4 Linux tests. Its uinput request numbers and the 92-byte `struct uinput_setup` equal the kernel values. Readiness requires the node and a descriptor held by an exact `system_server` process, and rejects mismatched device numbers, duplicate event nodes and malformed system names. On 10 November 2026, in the Docker LinuxKit kernel with `--device /dev/uinput`, a real proxy appeared under `/sys/devices/virtual` with the fixed name, the copied ID, event types `[0, 1, 4]`, exactly the three measured keys and `MSC_SCAN`. The inventory marked it virtual with no USB identity, enrollment and the policy matcher never selected it, and it disappeared on drop. The workspace passed 102 tests with that test included. On the reference phone the v14 services-hook run created the proxy, observed `system_server` open it in 6,865 ms, and confirmed `KEYBOARD | EXTERNAL` with `Generic.kl`, exclusion and teardown ([result](prototype-preflight.md#service-context-proxy-check-rerun-result-v14--10-november-2026)). Forwarded-event mapping is still untested.

The forwarding session has 3 end-to-end tests between two real uinput devices in the Docker LinuxKit kernel, one standing in for the physical node. Passthrough forwarded exactly scan, press, report, scan, release and report. While the session held the grab, a second reader on the source received nothing, and it received events again after the session stopped. The idle loop kept reporting progress. Stopping during a held key wrote the key-up and report to the proxy. A key held at grab time produced `NotNeutral`, forwarded nothing and released the grab. On 10 November 2026 the tests passed 10 consecutive reruns, and the workspace passed 110 tests with the real-uinput tests included. This is host evidence. The physical earphones, Android mapping and action equivalence are untested.

The supervised session has 4 Linux tests with real shell workers. A worker that starts and keeps reporting progress passes with exactly `[Start, Stop(Paused)]` and an orderly stop under 300 ms. A worker that never starts is a `StartTimeout` fault, not a pass. An unreadable gate starts nothing. The worker child stops at a closed gate, a gate error or a failed acquisition before sending any frame. The workspace passed 114 tests in the pinned container.

## Stage 4 preflight boundary

The standalone probe adds host checks for its command surface, safe SELinux reporting and private inactive marker. The supervisor crate now has a synthetic arm64 Linux ptrace smoke test for a child-owned info ioctl, with the exact environment and limits recorded in the [preflight plan](prototype-preflight.md); it is not a production tracer or Android evidence. An arm64 API 31 cross-build can establish the input-event ABI, ELF interpreter, linked symbols and segment alignment. EarKey Control device loading, intended-service access, proxy behavior, pause and input preservation remain physical checks. Record the exact reviewed commit, ELF digest, launcher and observed probe result for each authorized invocation. On 8 November 2026 the reviewed probe's shell-context `self-check` exited 0 on the reference setup (review head `ea71cfa`; ELF SHA-256 `bb9469338156678c53eec406903063bfe6c13a46e4377b5c6bfbdd72e24b2f42`), reporting AArch64, 4096-byte pages, 24-byte input events and enforcing `u:r:ksu:s0`. The temporary copy was removed and verified. On the same date the authorized temporary service diagnostic ran: the services hook stopped at the kernel-version guard (`KSU_KERNEL_VER_CODE=32704`; a fresh query also returned 32704), so the probe did not execute; the later boot-completed hook recorded 35240 and `guard_exit=0` but does not invoke the probe. The module was marked for removal and the cleanup reboot verified its paths, records and markers gone. A bounded follow-up found that the value changes during boot, so the discrepancy is temporal; the writer remains unidentified. The maintainer accepted the [composite identity check](decisions/0002-service-context-guard.md) on 10 November 2026 for the metadata-only launcher check. A read-only preflight later that day measured a new built-in kernel profile (`4.14.357-reforge-g9b21e3df6c0a`, build `#2 SMP PREEMPT Mon Nov 9 19:36:49 WIB 2026`, `full_version=v4.2.0-35201-backslashxx`, flags `0x160`, features `0x7`), and the maintainer selected a re-baseline to that profile. The authorized 10 November v8 run stopped at the services-hook `full_version` guard before the probe ran. The maintainer then made `full_version` an observation. The host fixture has 22 passing tests and the deterministic v9 package is prepared, and the service-context launcher check is Passed. The authorized 10 November v9 run passed it: the services hook ran `self-check` with `probe=self_check_ok` and exit 0. `probe-uinput`, evdev access, grab, proxy behavior, pause and input preservation remain Not run.

## Performance and transition measurements

Project budgets are idle CPU **<0.1%** over a defined five-minute sample, worker memory **<15 MiB**, and added passthrough latency **p95 <20 ms** on the reference phone. These are acceptance targets, not results or upstream guarantees.

Proposed method: compare matched baseline and active five-minute idle samples with identical screen/audio/connection conditions, recording process CPU time divided by elapsed wall time as percentage of one core; report supervisor separately and aggregate wake sources. Sample worker RSS and report peak/steady state without conflating cache/PSS. Use monotonic physical-receipt and proxy-emission timestamps to measure per-frame forwarding delay; separately correlate Android action timing against unfiltered baseline so queue delay and framework latency are not hidden. Record sample count/distribution, instrument clock/overhead and tracing effect. Final instrumentation must be validated before claiming the latency budget.

Measure startup, hotplug, policy-transition, failure and recovery inactive windows and immediate-pause/grab-release time, including held keys and output stalls. Choose finite safety deadlines before Stage 4 and fault-test them; this specification does not supply measured values. No persistent wakelock or high-frequency polling. Investigate every idle wake source.
