# Release process and authority

Maintainer decision, 4 November 2026: MIT source, public repository `AmanSikarwar/earkey-control`, **release when everything is implemented**. No installable release is authorized or eligible in Stage 0. Source publication and a documentation PR are distinct from publishing a module release. A release still requires specification acceptance; completed source alone is insufficient.

1. Close all critical blockers: wrong-device capture, input loss, audio/microphone regression, policy/security flaws, boot delay and unreliable recovery. Complete intended stable features and applicable physical/environment evidence; keep missing manager/hardware rows truthful.
2. Use a release PR to align README, changelog, support matrix, recovery/install/rollback instructions, notices, version and monotonically increasing integer versionCode across stable/prerelease ordering. No version is assigned in Stage 0. Confirm actual repository merge/review/check policy and disclose missing independent review where relevant.
3. Select the exact clean reviewed main commit after required checks. Build and inventory final assets with pinned tooling, compare two clean builds, generate checksums/notices/provenance, and record digests **before** physical acceptance. Changed bytes require affected acceptance again.
4. Physically test those exact bytes on named combinations using T01–T28 and minimum counts. KernelSU reference is first. Magisk/APatch require their own truthful support status; neither inherits reference results. No stable claim based on install success or a wording change.
5. Create an annotated tag on the accepted commit. Sign only if the maintainer has an established signing identity and verification process. Do not invent a signature or move published tags.
6. Prepare a **draft prerelease** with installable ZIP (not GitHub source archive), SHA-256 checksums, actual notices/dependency inventory and available provenance. Explain tested Android/root/accessory combinations, capabilities/shared effects, inactive windows, known limits, installation and recovery/rollback.
7. Run a bounded beta with explicit cases and sanitized reporting. Resolve critical input/audio/boot/recovery issues before stable publication. Current public-source authorization is not authorization to skip implementation, beta or stable gates.
8. Before publication verify the maintainer's policy applies to the concrete candidate, all implementation/acceptance requirements are complete, every asset is present, and signing/attestation/immutable-release controls actually exist. If immutable releases are enabled, attach assets while draft; do not publish incomplete locked assets.
9. After authorized publication, download public assets and verify digest and tag/commit association. Test actual manager update descriptors; human version, integer ordering, versioned ZIP URL and changelog must agree. No custom background downloader or executable fetch at boot.
10. Retain last known good artifact and its evidence. Correct faulty releases through an advisory, new version or explicit rollback; never replace bytes behind an existing version or silently reuse an old tested digest.

Support rows need evidence-backed Verified/Experimental/Design target/Unsupported labels. Stable overall status requires the definition of done in specification §20. Missing physical environments remain openly unverified; ask the maintainer to resolve any release-scope conflict rather than declaring the missing acceptance complete.

GitHub account/plan capabilities and branch protections must be verified, with checks and review suitable for a solo maintainer (no impossible self-approval). Available attestations establish source/build provenance, not safety or hardware success. Primary guidance: [secure Actions](https://docs.github.com/en/actions/reference/security/secure-use), [protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches), [immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases).
